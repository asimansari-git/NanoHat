## 🎯 Objective & Problem Statement

### 1. The Architectural Pivot: Systems Engineering Over Brute-Force Fine-Tuning
In v1 and v2, NanoHat attempted to solve autonomous OS actions by heavily fine-tuning `SmolLM2-360M` on synthetic multi-turn datasets. However, fine-tuning alone could not overcome the fundamental attention limitations of sub-1B parameter models when presented with a large, 16-tool system schema (context dilution, schema confusion, syntax hallucinations).

In **v3.0.0**, the architecture pivoted to a first-principles systems engineering paradigm:
1. **Model:** Switched to stock `functiongemma:latest` (268M Q8_0, ~600MB RAM footprint) using native tool-calling control tokens.
2. **Intent-Based Dynamic Tool Gating (`runtime/router.py`):** Pre-compiled regex intent clusters detect query intent and dynamically filter the 16-tool catalog down to **1–4 candidate tools** per turn.
3. **Dynamic System Prompt Assembly (`runtime/prompts.py`):** Assembles a lean system prompt containing instructions *only* for the active tools for that specific turn, completely preventing inactive tool hallucinations.
4. **Persistent State Engine (`runtime/db.py`):** Thread-safe, concurrency-safe SQLite database running in **WAL mode** at `~/.local/state/nanohat/state.db` for user memory and scheduled tasks.
5. **Zero External Framework Overhead:** Built entirely with standard library Python (`urllib.request`, `ast`, `sqlite3`, `argparse`, `psutil`).

### 2. Pre-Release Polish: Neutralizing Attractor Bias in `task_add`
- **Diagnosed Issue:** FunctionGemma 270M exhibited copy-attractor bias when given queries like `"Remind me for coffee in 3 minutes"`, copying `'tomorrow at 10am'` verbatim from the schema description in `runtime/tools.py` line 247.
- **Resolution:** Neutralize parameter descriptions in `runtime/tools.py` and `runtime/prompts.py` to prompt raw temporal phrase extraction (`"Extract the exact time expression or relative duration mentioned by the user"`), allowing Python backend logic to handle date/time computation.

NanoHat v3.0.0 is a major architectural leap that transforms NanoHat from an experimental fine-tuning research pipeline into a lightweight, zero-training, sub-300M parameter autonomous Linux OS agent running with sub-second CPU latency.

By applying **systems engineering first**, v3.0.0 solves the critical context dilution bottleneck of sub-1B models: instead of overwhelming a small model with 16 complex tool schemas, NanoHat dynamically routes queries through a fast regex classifier and injects only 1–4 candidate tools into the attention window per turn.

### Key Architectural Highlights
1. **Zero Fine-Tuning Required:**

   - High-speed deterministic regex classifier routes incoming queries to candidate tool clusters (Math, Datetime, Radios, Services, System Health, Housekeeping, Memory, Tasks).

   - Concurrency-safe local storage at `~/.local/state/nanohat/state.db`.

   - Standard library Python (`urllib.request`, `ast`, `sqlite3`, `subprocess`, `argparse`) + `psutil`.

# 🎩 NanoHat v3.0.0: The Sub-300M Zero-Shot OS Agent

> *"Fine-tuning is the last resort. First, try all methods of systems engineering."*

We are proud to release **NanoHat v3.0.0**—an ultra-lightweight, private, offline-first autonomous OS agent that runs locally on standard CPU hardware with a **~600MB RAM footprint** and sub-second latency.

---

### 💡 The Core Breakthrough: Intent Routing vs. Context Dilution
When building sub-1B parameter agents, the fundamental failure mode is **context dilution**. Exposing a 270M model to 16 complex tool schemas simultaneously causes attention diffusion, schema confusion, and syntax breakdowns.

In v3.0.0, we bypassed brute-force fine-tuning and solved this through **clean systems architecture**:
1. **Stock FunctionGemma 270M**: Uses native tool-calling control tokens out-of-the-box.
2. **Dynamic Intent Pruning**: A lightning-fast regex router analyzes user intent and filters the tool catalog down to 1–4 candidate tools per turn.
3. **Dynamic Prompt Assembly**: Injects instructions *only* for the active tools, keeping prompt overhead under 120 tokens.
4. **Deterministic OS Execution**: 16 safe, sandboxed OS functions covering system telemetry, systemd user services, power profiles, Wi-Fi/Bluetooth, persistent memory, and task scheduling.

---
